# Home automation and the Sonoff coordinator

This runbook brings up Home Assistant, authenticated MQTT and Zigbee2MQTT as
three separate acceptance checkpoints. All releases are represented in
Helmfile but are disabled in `cluster/helmfile-values.yaml` until deliberately
enabled. A normal platform sync therefore cannot claim an unknown USB device.

## Accepted architecture

The installed Sonoff coordinator is a zStack device, commonly sold as the
ZBDongle-P. Zigbee2MQTT is the sole owner of the coordinator; do not configure
Home Assistant's ZHA integration against the same device.

```text
Sonoff zStack USB on Titan
          |
          | /dev/serial/by-id/... mounted as /dev/zigbee
          v
 Zigbee2MQTT (zigbee namespace, USB exception)
          |
          | authenticated MQTT
          v
 Mosquitto (smart-home namespace) <----> Home Assistant
          |
          +---- logs collected by Alloy; health visible in Kubernetes/Grafana
```

Zigbee2MQTT is preferred to ZHA for this homelab because it supports a broad,
mixed device catalogue, gives better interview and mesh diagnostics, and keeps
the Zigbee network alive across Home Assistant restarts. The cost is one small
MQTT broker and a second stateful application.

The boundaries are intentional:

- Home Assistant and Mosquitto run under baseline Pod Security in `smart-home`;
- only Zigbee2MQTT runs in the privileged `zigbee` namespace;
- Zigbee2MQTT is pinned to Titan by hostname and the
  `hardware.6940469.xyz/zigbee-coordinator=true` capability label;
- Mosquitto accepts only the Home Assistant and Zigbee2MQTT pods;
- anonymous MQTT is disabled and per-client passwords are generated by Butler;
- Butler stores MQTT credentials, the Zigbee network key and frontend token in
  Vault; VSO creates only the namespace-local Kubernetes Secrets;
- the frontend uses its own Vault-generated token and the shared wildcard TLS
  certificate at `zigbee.6940469.xyz`;
- pairing starts closed and is opened temporarily from the Zigbee2MQTT UI.

Home Assistant does not provide a suitable native OIDC flow for this design.
Use its native owner account with MFA; do not put a generic Pocket ID forward
auth layer in front of the companion-app API. Zigbee2MQTT likewise uses its
native frontend token until a tested OIDC-aware proxy exists.

## Physical preparation

Connect the Sonoff through a USB extension cable and place it away from Titan,
USB 3 devices and the Wi-Fi access point. This reduces 2.4 GHz interference.
Do not flash coordinator firmware merely because a newer image exists: first
record the current firmware, read the zStack release notes and take a backup.

Find the stable device identity through the supported CLI entry point:

```bash
homelabctl node connect titan
ls -l /dev/serial/by-id/
udevadm info --query=property --name=/dev/serial/by-id/REPLACE_WITH_SONOFF_ENTRY
exit
```

The path should identify an ITead/Sonoff Zigbee 3.0 USB Dongle Plus. Stop if
there is no `by-id` entry, if the link disappears after reconnecting the
dongle, or if it resolves to an unexpected device. Never commit `/dev/ttyUSB0`:
that number can change after a reboot or another USB serial device is added.

Copy the exact `/dev/serial/by-id/...` path into
`cluster/helmfile-values.yaml`. Keep `adapter: "zstack"`.

Before forming the Zigbee network, inspect the router's 2.4 GHz Wi-Fi channel.
The repository starts on Zigbee channel 20, a broadly compatible ZLL channel.
Change it before pairing if the local radio survey shows a collision. Changing
the network key requires every device to be paired again; channel changes can
also leave sleeping or marginal devices behind.

## Increment 1: Home Assistant

Set only this switch:

```yaml
smartHome:
  homeAssistant:
    enabled: true
  mqtt:
    enabled: false
  zigbee2mqtt:
    enabled: false
```

Then preview and apply the exact release:

```bash
homelabctl deploy diff
homelabctl deploy apply home-assistant
homelabctl cluster status --all-pods
```

Open `https://ha.6940469.xyz`, create the owner account, enable MFA and set the
internal and external URL to that same HTTPS address. The chart writes only a
first-boot `configuration.yaml`; once it exists on the PVC, Home Assistant owns
it and Helm upgrades do not overwrite it.

Host networking is deliberately off. Direct-IP LAN integrations work through
the allowed LAN egress, but mDNS/SSDP discovery may not. Add devices manually
at first. Enabling host networking later is a security decision because it
binds port 8123 directly on Titan and weakens NetworkPolicy isolation.

Do not continue until the PVC exists, login survives a pod restart and a first
encrypted off-node backup of `/config` has been tested.

## Increment 2: Mosquitto

Set `smartHome.mqtt.enabled: true`, then run:

```bash
homelabctl deploy diff
homelabctl deploy apply mosquitto
homelabctl cluster status --all-pods
```

Butler reconciles the `ManagedCredential` at `smart-home/mqtt`. VSO projects
the two clients into `smart-home/mqtt-credentials`, and an init container
builds Mosquitto's hashed password file. Password rotation restarts Mosquitto;
coordinate it with both clients rather than rotating during an automation
incident.

In Home Assistant, add the MQTT integration with broker
`mosquitto.smart-home.svc.cluster.local`, port `1883`, and the
`home-assistant` credential from Vault path `secret/smart-home/mqtt`. Use the
Vault UI authenticated through Pocket ID for this one-time entry; do not print
the password into a terminal transcript or commit it.

## Increment 3: Zigbee2MQTT

The hardware label is already part of Titan's private Ansible inventory and
the reusable example. Reconcile it before scheduling the pod:

```bash
homelabctl cluster snapshot save --name before-zigbee-label --ask-become-pass
homelabctl cluster bootstrap --limit titan --ask-become-pass
homelabctl cluster nodes
```

Verify the node output contains
`hardware.6940469.xyz/zigbee-coordinator=true`. Then set the exact device path
and enable the release:

```yaml
smartHome:
  mqtt:
    enabled: true
  zigbee2mqtt:
    enabled: true
    device: /dev/serial/by-id/REPLACE_WITH_EXACT_SONOFF_ENTRY
    adapter: zstack
```

The chart rejects an empty path, a `ttyUSB` path and any adapter other than the
reviewed `zstack`/`ember` values. Apply and inspect:

```bash
homelabctl deploy diff
homelabctl deploy apply zigbee2mqtt
homelabctl cluster status --all-pods
```

Open `https://zigbee.6940469.xyz` and use the frontend token from Vault path
`secret/smart-home/zigbee2mqtt`. Confirm the coordinator starts as `zstack`,
MQTT connects, Home Assistant discovery is enabled and `permit_join` is false.

Pair one mains-powered router/switch first, then one battery device. For each
of the random switches, check the upstream supported-device page, factory reset
the device, open pairing only for the interview, assign a stable friendly name
and close pairing again. Add mains-powered routers before distant battery
devices so the mesh grows outward from the coordinator. Prefer Zigbee groups
for multi-light actions; they continue to work more reliably than a burst of
individual commands.

## State, backup and restore

Three PVCs have different recovery value:

| PVC | Contents | Recovery priority |
| --- | --- | --- |
| Home Assistant config | configuration, SQLite state, automations and integrations | critical |
| Zigbee2MQTT data | device database, coordinator backup, names and runtime configuration | critical |
| Mosquitto data | retained MQTT messages and broker persistence | useful but rebuildable |

Vault is the source for generated MQTT passwords, the frontend token and the
16-byte Zigbee network key. Zigbee2MQTT also renders the key into its protected
runtime configuration because the coordinator process needs it. Back up the
whole data directory together; never commit `configuration.yaml`,
`database.db`, `coordinator_backup.json` or any exported network key.

To recover, stop Zigbee2MQTT so no process owns the serial device, restore its
PVC and Vault material together, reconnect the same coordinator, verify the
same stable path and only then start the pod. A mismatch between the restored
PAN/network values and the coordinator can force a full re-pair, so never
delete `coordinator_backup.json` as a casual troubleshooting step.

## Operations and failure policy

- Keep physical controls for essential lights; Titan downtime must not make a
  room unusable.
- Do not enable automatic Zigbee device OTA updates. Review and update one
  device class during a maintenance window.
- Snapshot application data before Home Assistant or Zigbee2MQTT upgrades and
  keep the prior image tag available for rollback.
- Alloy collects container logs into Loki. Kubernetes pod/PVC health appears in
  the shared dashboards; component-specific MQTT and Zigbee metrics remain a
  follow-up after real load is measured.
- If the coordinator disappears, inspect the host path and USB connection
  before restarting repeatedly. Repeated crash loops can obscure the original
  serial error.
